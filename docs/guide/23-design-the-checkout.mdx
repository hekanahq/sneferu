# 23. Design the checkout

The checkout page is part of your theme: it has your header and footer, your
tokens, your fonts and your CSS. The checkout itself is not. Hekana's own
checkout (contact details, delivery address and rates, the order summary,
payment) is mounted on the page where your checkout tags sit. Every price, rule,
validation and payment field belongs to Hekana, so a theme can restyle the page
around it and can never read or change the money path.

Hekana turns the themed checkout on per store. Until it is on for a store, that
store keeps Hekana's standard checkout page.

## What you write

| File | Role |
| - | - |
| `templates/checkout.snf` | The page. Usually `<hk-sections />` plus a `<hk-schema>` listing the default sections |
| a section whose `<hk-schema>` has `"templates": ["checkout"]` | The content: a heading, trust notes, and the checkout tags |

A theme with no `templates/checkout.snf` gets the SDK's default checkout, so the
page is themed from the first day. `sneferu init` writes both files.

A section may sit on the checkout page only if its `templates` list names
`checkout`. A section with no `templates` list is offered everywhere else, but
never here (SN3041 for a default, and the builder does not offer it).

## The five tags

You place `<hk-checkout-layout>` and the four parts inside it. The tags print
only an empty mount point and your presentation choices.

| Tag | Props |
| - | - |
| `hk-checkout-layout` | `columns`: `two` (default) or `stacked`. `summary`: where the order summary sits, `end` (default; right in English, left in Arabic), `start` or `top` (full width above the form). `sticky`: keep the summary in view while the form scrolls (two columns, wide screens; default true). `density`: `comfortable` or `compact`. `card`: `outlined`, `flat` or `raised` |
| `hk-checkout-contact` | `heading` (up to 60 characters) |
| `hk-checkout-shipping` | `heading` |
| `hk-checkout-summary` | `heading` |
| `hk-checkout-payment` | `heading`, and `cta-label` (up to 40 characters), the text of the confirm button |

Details:

- **Order.** The order of the contact, shipping and payment tags inside the
  layout is the order of those parts in the form. A part you leave out still
  appears, in its default place, with Hekana's own title: you cannot remove a
  part of the checkout.
- **Headings.** A part with no `heading` (or an empty one) keeps Hekana's title.
  Headings and the button label are plain text, cut to their limit.
- **Button label.** `cta-label` applies only to cash on delivery. A payment
  method that names its own button keeps its own text.
- **Presentation only.** None of the props can change an amount, a field, a
  rule or a payment method.

## Rules the compiler enforces

| Rule | Code |
| - | - |
| The checkout tags go in `templates/checkout.snf` or a section that lists `checkout` only | SN2030 |
| Each tag appears once on the page | SN2031 |
| The page needs a layout holding `<hk-checkout-payment>` | SN2032 |
| Parts are direct children of the layout | SN2033 |
| Only layout, typography, image and link tags, plus the checkout tags | SN2034 |
| No cart, product, order, customer or catalogue data, and no `money` filter | SN2035 |
| No `audio`, `video` or `track` (forms, inputs, buttons and scripts are not on the element allow-list at all, SN2001) | SN2036 |
| A checkout section has no `product` or `collection` setting | SN2037 |
| Links stay in the store (or go to chat and social profiles) | SN2038 |
| No inline `style`, no `id`, `name` or `data-hk-*` on plain elements | SN2039, SN2040 |
| The layout sits in page structure only, never inside a link or `<details>` | SN2041 |

The allowed `hk-*` tags on the page are `hk-section`, `hk-container`,
`hk-stack`, `hk-grid`, `hk-heading`, `hk-text`, `hk-rich-text`, `hk-image`,
`hk-button`, `hk-card`, `hk-badge` and `hk-icon`. Expressions start from
`settings`, `section`, `block`, `store`, `request`, `localization`, `locale` or
`dir`. The same rules apply to the blocks and snippets a checkout section
reaches. The page has no cart total to print: Hekana prints every price.

## Fails closed

- A page that does not place a layout with `hk-checkout-payment` renders
  Hekana's default checkout page, not an empty one.
- If the page fails to render, Hekana's default checkout page is shown instead.
- A second copy of a checkout tag (a merchant adds the section twice) is
  skipped, as is a tag outside the checkout page or a part outside the layout
  (SN4015, SN4016, SN4017).
- Section groups (header, footer) never print checkout tags.

## What else is on the page

The shared header and footer groups render as on every page. Your theme CSS
applies to the page. Theme JavaScript is never loaded on checkout routes.
The payment step runs in Hekana's own components.

## A dark, compact variant

Layout props take the same values from settings, so a theme can offer them to
the merchant. For a dark store the colours come from the tokens; the checkout
form follows them.


```html title="a dark compact layout"
<hk-checkout-layout columns="two" summary="end" density="compact" card="flat" sticky="true">
  <hk-checkout-contact />
  <hk-checkout-shipping />
  <hk-checkout-summary />
  <hk-checkout-payment />
</hk-checkout-layout>
```

```css title="assets/theme.css"
.sf-checkout-section { background: var(--hk-color-background); color: var(--hk-color-text); }
```


## Stacked, summary on top


```html title="a stacked layout"
<hk-checkout-layout columns="stacked" summary="top" sticky="false" card="outlined">
  <hk-checkout-payment heading="Pay" />
  <hk-checkout-contact />
  <hk-checkout-shipping />
  <hk-checkout-summary />
</hk-checkout-layout>
```


Here the payment tag comes first, so payment is the first part of the form
under the summary.

## Preview

`sneferu dev` serves `/checkout` (and `/en/checkout`, `/ar/checkout`). It has no
checkout of its own, so it draws labelled boxes where the checkout will sit,
laid out as your props ask, with a note that it is a preview. The boxes hold no
fields and no prices. If the page places no usable layout, the preview says that
a store would show Hekana's default checkout instead.

## In the builder

A merchant finds Checkout in the page switcher. The section that holds the
checkout tags is shown as Hekana's checkout: locked, with a note that Hekana
handles payments. It cannot be deleted, hidden or duplicated, but its settings
(headings, layout, copy, colours) are edited like any section's, and other
checkout sections can be added around it. The builder preview shows the same
labelled boxes as `sneferu dev`.

## What the checkout page strips

The shopper is about to type a phone number and pay, so the rendered checkout page is filtered as a whole, header and footer included: any link that leaves the store is printed as `#` (store paths, anchors, `mailto:`, `tel:` and https links to chat and social sites stay), and inline `style` attributes are dropped. A section that does not list `checkout` in its `templates`, and a block the section does not allow, are skipped on this page. A page whose layout would sit inside a link, a `<details>` or any other element than page structure is refused, and the store shows Hekana's default checkout instead.
